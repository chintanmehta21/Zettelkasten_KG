## Rollback procedure (only if smoke test fails or prod regresses)

The redesign is additive at the SQL layer (new RPCs + new index + new cron
job + a relaxed CHECK that is a strict superset of the old one). Rollback is
therefore non-destructive to data, but the application code at HEAD assumes
the new RPCs are present — operator MUST also redeploy the prior application
image.

```sql
-- 1) Drop the new state machine RPCs:
DROP FUNCTION IF EXISTS core.ops_accept(uuid, text, text, jsonb, int);
DROP FUNCTION IF EXISTS core.ops_start(uuid, text);
DROP FUNCTION IF EXISTS core.ops_finalize(uuid, text, text, jsonb, jsonb);

-- 2) Drop the partial unique index (CONCURRENTLY also OK here):
DROP INDEX IF EXISTS core.ops_user_req_hash_active_uniq;

-- 3) Unschedule the stuck-running reaper:
SELECT cron.unschedule('reap_stuck_running_operations');

-- 4) (Optional) restore the original CHECK constraint to reject the new
--    lexicon values. ONLY do this if a prior app image will be redeployed
--    that emits the old 'accepted'/'succeeded'/'failed' set; otherwise leave
--    the relaxed CHECK in place (it allows everything the old code emits).
ALTER TABLE core.operations DROP CONSTRAINT IF EXISTS operations_status_check;
ALTER TABLE core.operations
  ADD CONSTRAINT operations_status_check
  CHECK (status IN ('accepted','succeeded','failed'));
```

Then redeploy the prior application image (the master tag immediately before
this PR merges) via the normal `deploy.sh` path. The blue/green flow makes
this a single Caddy reload.

## Estimated risk

**Low.** Justification:
- `core.operations` is a small table (sub-MB at current production load); the
  CHECK swap + status backfill complete in sub-second.
- The partial unique index is built `CONCURRENTLY` (no table lock); on the
  current row count it completes in single-digit milliseconds.
- The new RPCs are additive; the old code path simply stops being called once
  the new application image is live (no SQL-level coupling between the two).
- The pg_cron job has the same `IF NOT EXISTS` idempotency guard as job 49.
- All three RPCs are `SECURITY DEFINER` + `GRANT EXECUTE TO service_role`
  only — no widening of the RLS posture.
